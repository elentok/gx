# Design coupling inventory for a shared stepped-session model

Question (`gx:triage-followups-ui/01`): which places assume that a stepped session is a Design on a map epic, and what does each need to take a flow kind (Design or Triage)? Read from source on branch `triage-followups-ui-design`, 2026-11-08. All paths are relative to the repo root.

## Headline findings

1. **Three different things are fused under "Design".** (a) The step list and its state, stored as the map epic's `design_step`. (b) The session marker `meta.Design`, set only when the linked ticket is on a map epic. (c) The Design's identity: the map epic address, which the web route, session lookup, hold, workspace placement and card all key on. A Triage has no map epic, so it has none of the three. Generalizing means giving each its own flow-kind-aware home, not adding a second step list.
2. **`meta.Design` (bool) is the gate for almost every session behavior.** Continue, auto-advance, the run-end Actionable, the `AskUserQuestion` ban, the Design page lookup, hold, workspace membership, token group, Grilling stats and the Agents tab label all read it. A Triage session would get none of them unless the flag becomes a flow kind (or a second flag is added in every place).
3. **The step list lives in `tickets`, not in the session layer.** `tickets.DesignSteps` is read by the epic loader, `gx tickets set`, the card percent, `gx agent context-window --fits` and the migration guesser. The wire `ProgressStep` is a type alias of `tickets.DesignStep`. A Triage step list must not go into `design_step`: the loader refuses unknown values and `set` refuses non-map epics.
4. **A Triage has no epic to hold its state.** `follow-ups` is a loop epic; map-only fields are refused on it. State must live in a new record or a new epic field (ticket 03). Every new epic field forces a `migrations/steps.go` step through the schema guard.
5. **The Continue prompt is hardcoded to `gx-design`** in three Go places plus the skill's own text. The run-end line regex is generic (`✅ X: ... Next: ...`), so it needs no change.
6. **The final-step rule is wrong for any other step list.** `DesignFinal` and `designStep` hardcode Branch or Done as "final".
7. **Unknown ledger groups fold into Other.** `ledgerGroups` maps any group not in `costGroups` to Other (`server/stats/statscost.go:139-141`), so a "Triage" group needs the list, the web color map and the poller changed together.
8. **No worktree or branch assumption is needed by Triage, but the launch path forces one.** `openDesign` always calls `resolveDesignDir`, which makes or rebases `<epic>-design`, or returns the trunk checkout after Branch (`server/designs/designs.go:90-110,359`). A Triage launch must skip this and use the trunk checkout directly.

## State: /clear, server restart, worktree

How Design state survives today:

- **Across `/clear` and `/new`:** the step, the destination and findings live in the map epic's `ticket.md` (`design_step`, body sections `Destination`, `Review findings`, `Not yet specified`) and its tickets, never in the conversation (`skills/gx-design/SKILL.md:21-22,148-149,236-246`). Detection re-reads them each run. `StartContinue` types `/clear` then the skill command into the same gx session (`sessionhandoff.go:16-24`, `chat/actionable.go:25-33`). The conversation id changes under the session: the watcher saves the old conversation's totals and records the new one (`sessionwatch.go:180-186`). `ReportedStep` clears whenever the session becomes promptable (`sessionwatch.go:171-173`).
- **Across a server restart:** `meta.json` holds `Design`, `LaunchDesign`, `Ticket`, `Tier`, `ReportedStep`, `AutoAdvanceOff`, `AutoSends`, `Actionable`, `FirstPrompt`. The auto-advance countdown is memory only: a restart drops it and leaves the Continue raised (`prompt/autoadvance.go:27-28`). `ScanCleanups` tracks the last seen step in memory (`designSteps.Swap`) and the ready message uses a persisted mark (`designready.go:11-12,28-42`) so a restart does not repeat it. A Resume restarts the harness for the same session (`startSessionHolder`, `sessions.go:270-290`).
- **Worktree and branch:** only Design. Past Branch the session runs in the trunk checkout, so even Design does not need a worktree for its late steps (`designs.go:96-103`).

For a Triage, the step and the plan must be in a durable record outside the conversation (ticket 03), because `/clear` between steps is the point. The skill must re-derive "where am I" from that record and from the follow-ups' own state, and the "never write a row twice" rule needs a per-row done marker in the record. The live-session lookup needs the persisted `Ticket` and flow on `meta.json`.

## Notes that change the grilling tickets

- **02 (steps and boundaries):** a `fits` growth value per Triage step is required, or auto-advance cannot chain Triage steps (`agent_fits.go:20-30`). Ask which Triage step runs the verify subagents and how that one is split across sessions.
- **03 (state):** Triage cannot reuse `design_step` (loader refuses unknown values; `set` refuses non-map epics). Decide between a new `follow-ups` epic field (migration step, snapshot change) and a separate record. Also decide what "Triage opens the live one" keys on: `Ticket` on `follow-ups` plus a flow kind is enough for the server lookup.
- **04 (shared model):** the model needs four hooks beyond the step list: final-step rule, skill and argument for Continue, identity (map address vs project), and the Design-only slots (impl link, tickets sub-tree, worktree launch). `meta.Design` as a bool is the main thing to replace, and every gate listed above reads it.
- A Triage session's `Ticket` would be `project:follow-ups`, which is a loop epic that has no card; workspace `place` (`membership.go:81-96`) and the epics `designActivities` fold would treat it as an epic placement unless taught otherwise.
- The plan view's inline questions are structured data from the skill, not chat blocks, so they do not use the Grilling parser; the Triage skill "never grills" (`skills/gx-triage-follow-ups/SKILL.md:17`).
